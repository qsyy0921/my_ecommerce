# 审计文档碎片化风险审计

## 背景

继续审核时，我不再只看单篇文档是否正确，而是开始看这一整批审计文档组合起来是否还易读、易维护。

当前 `docs/sdd` 下已经累计了很多按日期命名的审计文档。仅 `2026-05-31-*.md` 就有一整批，分别覆盖：

- 剩余 DDD/业务边界
- 代码热点
- 商城运营热点
- 模型和装配热点
- 通用网关和领域编排残留
- 拼团锁单等待策略
- 架构守护体系
- 文档证据漂移
- 八股文档同步漂移

这些文档单独看都成立，但组合起来开始出现一个新的问题：

- 审计结论越来越碎片化。

## 审计发现

### 1. 最近几轮审计已经从“补充事实”逐渐进入“拆分事实”

一开始按主题追加审计文档是合理的，因为每一轮都在发现新的剩余问题。

但现在的变化是：

- 很多文档讨论的是同一个大主题的不同切面；
- 各篇之间存在明显的概念交叉。

例如：

- `current-ddd-business-gap-audit` 讲剩余问题总览；
- `code-hotspot-audit` 讲热点类；
- `gateway-and-domain-orchestration-audit` 讲超宽接口和领域编排；
- `lock-idempotency-and-assembly-boundary-audit` 又聚焦到拼团锁单等待；
- `architecture-guard-hotspot-audit`、`documentation-evidence-drift-audit`、`interview-sync-drift-audit` 又转向守护和口径。

这说明现在问题已经不是“有没有记录”，而是“记录是否开始过度拆片”。

### 2. 跨文档重复关键词明显增加，入口阅读成本在上升

最近这批文档里反复出现的词已经很集中：

- `DomainPurityTest`
- `Redis Stream`
- `后续`
- `当前结论`
- `本轮结论`
- `不修改生产代码`

这不是坏事本身，但它说明：

- 很多审计文档之间已经共享一部分前提和结论；
- 读者如果从头逐篇读，会不断重新进入相似语境。

结果就是：

- 信息更完整了；
- 但入口理解成本也在提高。

### 3. 当前文档体系已经需要“总览型收敛”，否则会越来越像一串独立审计快照

现在最明显的结构问题是：

- 每篇单文档都能成立；
- 但跨文档还缺一个更高层的“剩余问题地图”。

`README.md` 现在只是索引，不负责聚类。
`tasks.md` 和 `ddd-sdd-todo-list.md` 更接近状态清单，不是阅读导航。

所以继续这样增长下去，最容易出现：

- 文档越来越多；
- 读者越来越不知道先看哪几篇；
- 同一个问题被不同文档以不同抽象层重复描述。

### 4. 当前最缺的不是再多一篇单点审计，而是“审计分组规则”

现在按主题继续细分没有错，但如果不加分组规则，后续会越来越难控制。

更合理的方向应该是：

- 把“代码剩余问题”类审计归一组；
- 把“守护与文档体系问题”类审计归一组；
- 把“对外口径与面试同步”类审计归一组；
- 或者在 `README.md` 里至少按类别分段，而不是继续只按文件名平铺列出。

## 审计结论

当前 SDD 文档体系已经不只是存在“证据漂移”问题，还开始出现“审计碎片化”问题：

- 单篇没问题；
- 组合起来阅读成本上升；
- 同主题结论分散在多篇文档里。

这属于信息架构问题，不是代码问题。

## 当前建议

本轮仍然只记录问题，不改造旧文档结构。

原因：

- 现阶段继续大改 README 或重组所有审计文档，成本偏高；
- 而且历史记录仍然有价值，不适合贸然合并。

但后续如果继续治理文档体系，更合适的动作是：

1. 在 `README.md` 里按主题分组现有审计文档，而不是继续平铺。
2. 在 `tasks.md` 或单独文档中增加“当前剩余问题地图”，把最核心的 5 到 10 个残留点收敛出来。
3. 继续新增审计时，优先判断是否真的需要新文档，还是应该补到现有同类文档里。

## 优先级判断

这个问题的优先级：

- 低于代码主链路风险；
- 高于继续无限追加新的单点审计。

因为如果审计文档继续碎片化，后续每增加一次审计，理解成本都会上升。

## 本轮结论

继续审核之后，现在已经可以明确说：

- 当前项目的风险不只在代码、测试和口径；
- 文档集合本身也开始出现结构性碎片化。

这意味着后续的“继续审核”如果再往下走，下一步更值得做的可能已经不是继续增加单点审计，而是开始治理审计文档的信息架构。

## 验收

- 本轮只新增审计文档，不修改生产代码。
- `README.md`、`ddd-sdd-todo-list.md`、`tasks.md` 同步记录本轮结论。
- Git 工作区保持可提交状态。

## 面试表述

这个点一般不直接在面试里展开，但如果面试官问到“你怎么做长期治理”，我会说：除了治理代码，我也在治理文档和审计体系。因为当审计文档积累到一定数量后，新的问题不只是有没有结论，而是结论是否开始碎片化。如果文档越来越多但阅读成本越来越高，长期维护一样会失控。
