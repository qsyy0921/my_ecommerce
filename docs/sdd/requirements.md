# 需求规格

## 业务范围

系统由支付商城和拼团营销服务组成。支付商城负责商品展示、下单、支付渠道选择、支付回调和订单列表；拼团营销服务负责拼团活动、秒杀活动、优惠试算、锁单、结算、退单和通知。

当前项目需要覆盖四条核心交易链路：

- 首页试算：用户进入商品页后查询营销配置，返回原价、优惠金额、实付金额、活动信息、可参与队伍和拼团统计。
- 拼团锁单：用户开团或参团时，营销服务校验活动、用户、人群、队伍和库存后创建拼团订单。
- 秒杀锁单：用户参与秒杀时，系统先用 Redis 原子预扣库存和用户占位，再写 DB 订单和活动库存。
- 支付结算与退单：商城支付成功后通知营销结算，营销服务判断成团或秒杀订单状态；超时未支付、已支付未成团、已支付已成团进入不同退单策略。

## 功能需求

### R1 首页试算

- 支持按 `userId + source + channel + goodsId` 查询拼团配置。
- 支持活动可见性判断，包括活动状态、时间窗口、渠道、商品。
- 支持人群标签过滤，不符合标签的用户不能看到或使用对应优惠。
- 支持优惠策略计算，返回原价、优惠金额、实付金额。
- 支持队伍列表和统计查询，用于商品详情页展示。

### R2 拼团锁单

- 支持开团和参团两种模式。
- 锁单必须是聚合行为，不允许绕过领域规则直接插入订单。
- 责任链必须校验参数、活动可用性、用户参与次数、队伍状态、队伍库存。
- 必须防止重复外部交易单、重复参与和队伍超卖。

### R3 秒杀锁单

- 秒杀活动必须有独立活动、价格、库存、限购和时间窗口。
- 秒杀锁单必须先在 Redis 完成库存预扣和用户占位。
- Redis 预扣必须是原子操作，不能把查库存、扣库存、用户防重拆成多个非原子命令。
- DB 必须保留条件更新和唯一索引，作为最终一致性兜底。
- Redis 成功但 DB 失败时必须回补 Redis 库存并释放用户占位。

### R4 支付渠道

- 支持支付宝真实支付和模拟支付。
- 模拟支付不依赖外部网关，用于本地开发、演示、压测和面试讲解。
- 支付成功必须先更新商城订单，再调用营销结算。
- 支付回调必须幂等，同一个支付单重复回调不能重复结算。

### R5 MQ 通知与补偿

- 成团通知、结算通知和退单补偿应通过 MQ 解耦。
- 消费者必须支持手动 ACK、重试、消费幂等和 DLQ。
- 业务失败不能无限重试阻塞主队列。
- 对账任务必须能发现商城订单、营销订单、支付结果之间的不一致。

### R6 可观测性与压测

- 所有入口请求必须携带或生成 traceId。
- 关键链路必须输出结构化业务日志。
- 必须暴露 Prometheus 指标，包括 QPS、RT、错误数、库存不足数、重复下单数、MQ 积压、DLQ 数量。
- 秒杀和拼团必须维护压测脚本与压测报告。

## 非功能目标

- 正确性：库存不超卖，订单不重复，支付不重复结算。
- 可用性：单个下游失败时，主链路可以降级、重试或进入补偿。
- 性能：秒杀查询链路走缓存，锁单链路先 Redis 后 DB。
- 可维护性：领域规则沉淀在领域层，基础设施只做适配。
- 可演示性：本地 JDK 1.8、Maven 3.8、Docker MySQL/Redis/RabbitMQ 可一键跑通。

## 验收标准

- `mvn -DskipTests package` 能在 JDK 1.8 下通过。
- 拼团、秒杀、订单、模拟支付页面可以互相跳转。
- 秒杀并发压测后满足 `available_count + lock_count = total_count`。
- MQ 消费支持幂等记录和 DLQ。
- 关键接口能通过日志或指标定位 traceId、用户、活动、订单、错误码。
