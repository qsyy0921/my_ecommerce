# 模型层与装配层热点审计

## 背景

在连续完成大仓储、大 Controller、消息端口和补偿支撑拆分之后，当前剩余的问题已经不再集中在“谁还在直接写 DAO、发 MQ、做补偿”这种硬伤上。

这一轮继续只读审计，目标是确认模型层、API DTO 和 app 装配层里是否还存在新的腐化热点，避免为了行数继续低收益重构，同时把真正值得警惕的点记录清楚。

本轮关注对象：

- `OrderStateTransitionEntity`
- `GroupBuyActivityDiscountVO`
- `GoodsMarketResponseDTO`
- `TradeRuleConfig`
- `MarketNode`

## 审计结论

### 1. `OrderStateTransitionEntity` 是共享状态迁移词典，不是当前必须继续拆的坏味道

当前 `OrderStateTransitionEntity` 里集中维护了秒杀订单、拼团订单、拼团队伍和售后状态的合法迁移工厂方法，并在 `of(...)` 中统一调用 `OrderStateMachine.check(...)` 做状态机校验。

这有两个优点：

- 领域状态迁移语义统一，仓储和支撑组件不再手拼状态流水。
- 非法迁移在创建阶段就被挡住，不会把不合法流水写进基础设施层。

但也要看到它的边界风险：

- 这个类已经同时承担多个 `bizType` 的迁移词典，后续如果继续叠加更多业务状态，容易变成共享大词典。
- 多个子域都依赖这个类，后续新增状态时要格外注意不要让一个子域的变化影响另一个子域的语义稳定性。

当前结论：不拆。

原因不是它已经完美，而是它现在仍然是“统一状态迁移词典”的单一职责，没有重新混入 DAO、MQ、缓存或事务细节。后续只有在新增更多业务类型、导致这个类继续膨胀成跨子域状态总表时，再考虑按 `bizType` 拆分为更小的 transition factory。

### 2. `GroupBuyActivityDiscountVO` 还保留字符串协议解析，是当前模型层最真实的残留问题

`GroupBuyActivityDiscountVO` 当前除了活动配置字段外，还直接持有：

- `tagScope` 字符串协议
- `isVisible()`
- `isEnable()`

它的问题不在于有行为，而在于行为依赖字符串协议解析：

- `tagScope` 仍是 `"1,2"` 这种编码约定，而不是结构化值对象。
- `isVisible()` / `isEnable()` 需要自己 `split` 和判断位置语义。
- 后续如果标签规则再扩展，最容易继续往这个值对象里堆更多协议分支。

这是当前模型层里最像“课程代码遗留协议”的位置。

当前结论：先记录，不立即改。

原因：

- 它现在只承担可见性/可参与性的规则解释，没有继续外溢到 Controller、Repository 或 MQ。
- 如果现在硬改成结构化协议，会连带改动试算查询、数据库映射和测试输入，收益不高。

后续更合适的演进方向是：

- 把 `tagScope` 从裸字符串演进成专门的 `TagScopeRule` / `TagScopeVO`。
- 让 `GroupBuyActivityDiscountVO` 持有结构化规则对象，而不是自己解析协议字符串。

### 3. `GoodsMarketResponseDTO` 仍有展示格式化逻辑，但问题级别低于领域边界问题

`GoodsMarketResponseDTO.Team` 里还保留了 `differenceDateTime2Str(...)`，负责把时间差格式化为倒计时字符串。

这个点不是领域污染，因为它在 API DTO 层，不在 domain 层。它的问题是：

- DTO 不只是数据承载，还带了展示格式化逻辑。
- 如果未来前端需要不同倒计时格式、国际化、毫秒级展示或“已结束/即将开始”多状态表达，这个静态方法会继续膨胀。

当前结论：不拆。

原因：

- 这已经比之前 Controller 里直接拼 DTO 好很多，格式化逻辑至少被收敛到 API 契约附近。
- 当前项目是本机演示型商城前端，不存在复杂国际化展示要求。

后续如果首页展示继续扩展，更合适的做法是把倒计时格式化收敛到 trigger/support 层的响应 assembler，而不是继续增强 DTO 自身。

### 4. `TradeRuleConfig` 是 app 装配热点，但还不是 DDD 腐化点

`TradeRuleConfig` 当前集中装配：

- 拼团锁单责任链
- 拼团结算责任链
- 拼团退款责任链
- 三类退款策略 Bean

这个类确实已经偏长，但问题性质需要说清楚：

- 它属于 app/config 层，本来就承担 Spring Bean 装配职责。
- 它没有重新混入业务执行、DAO 调用、缓存更新或消息补偿。
- 它当前更像“装配热点”，不是“领域污染”。

真实风险在于：

- 后续如果继续在同一个配置类里塞更多锁单/结算/退单/售后规则，它会逐渐变成总装配入口。
- Bean 命名、链路顺序和策略注册会越来越难审计。

当前结论：不拆。

更合适的治理方式不是继续抽空壳类，而是以后按场景拆成：

- `TradeLockRuleConfig`
- `TradeSettlementRuleConfig`
- `TradeRefundRuleConfig`

但这个动作要等规则继续增长时再做，现在收益不高。

### 5. `MarketNode` 仍保留显式异步编排，是领域服务里最需要持续盯住的点

`MarketNode` 已经通过 `IDomainTaskExecutor` 去掉了对线程池实现的直接依赖，但它仍保留：

- `FutureTask`
- 多线程查询活动配置和商品信息
- 超时控制
- 折扣服务 Map 路由

它现在不算 DDD 硬伤，原因是：

- 线程执行器已经端口化。
- 它仍然处在“首页试算领域服务”语义内。
- 这里的并发查询是明确的业务性能优化，而不是基础设施到处泄漏。

但它确实是后续最容易继续长胖的领域节点之一：

- 再加更多试算数据源时，异步编排复杂度会继续升高。
- `discountCalculateServiceMap.get(...)` 这种按字符串路由的方式，长期也容易变成隐藏扩展点。
- 当前父类/子类双实现（`MarketNode` / `MarketNode2CompletableFuture`）说明这里已经有技术实现分叉。

当前结论：只审计，不继续拆。

后续触发治理的条件应当是：

- 试算需要增加第三个以上异步数据源。
- 试算编排开始出现补偿、缓存回填、熔断降级等更强技术流程。
- 折扣路由不再只是简单 `marketPlan -> service`，而需要更明确的策略注册模型。

## 综合判断

这轮看到的剩余问题，重要性排序是：

1. `GroupBuyActivityDiscountVO` 的字符串协议解析残留。
2. `MarketNode` 的显式异步编排和技术实现分叉风险。
3. `OrderStateTransitionEntity` 的共享状态迁移词典后续可能继续膨胀。
4. `TradeRuleConfig` 的 app 装配热点风险。
5. `GoodsMarketResponseDTO` 的展示格式化逻辑。

其中只有第 1、2 项需要长期重点盯住；第 3、4、5 项目前更适合作为“观察点”，不值得现在继续改动生产代码。

## 本轮结论

本轮不做生产代码拆分。

原因很明确：这些点当前都不是会直接破坏 DDD 分层的硬伤，继续修改只会进入低收益整理。更合理的做法是把它们记录成后续观察热点，并在新增业务需求时优先复查这些类是否跨越了当前边界。

## 面试表述

我不会把当前项目包装成“所有类都已经拆到完美”。现在真正剩下的更多是模型协议和装配热点问题，而不是明显的 DDD 违例。比如拼团活动折扣值对象里还保留了 `tagScope` 字符串协议解析，首页试算 `MarketNode` 还保留显式异步编排，这些我会诚实说明为后续重点治理点；但像 `TradeRuleConfig` 这种 app 层装配热点，我不会为了行数机械拆掉，因为它暂时没有越过装配层职责边界。
