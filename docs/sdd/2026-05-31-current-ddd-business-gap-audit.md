# 当前剩余 DDD 与业务问题审计

## 背景

项目已经完成一轮大规模 DDD 治理：

- 商城和营销两个服务的 domain 包已去 Spring 注解。
- 拼团和秒杀的通用大 Repository 已删除，核心写模型、读模型、库存、补偿、MQ、对账都拆到了独立端口或支撑组件。
- `DomainPurityTest`、状态机测试、拼团锁单/退单和秒杀库存单元测试已经补齐。

当前继续机械拆分类和端口的收益已经明显下降。下一步更重要的是明确“还存在哪些问题”，区分：

- 代码边界问题。
- 业务能力问题。
- 只有本机时无法继续消除的生产边界。

## 结论

### 一、当前主要不是 domain 污染问题，而是入口编排和基础设施大类问题

项目当前最明显的代码层风险不在 domain 层，而在 trigger/support 和 infrastructure 公共适配层：

- 拼团和秒杀入口支撑组件仍然偏厚，例如 `GroupBuyLockOrderSupport`、`SeckillLockOrderSupport`、`SeckillManualCompensationOpsSupport`。
- Redis 公共适配层仍然偏大，`IRedisService` / `RedissonService` 更像通用技术工具箱，而不是收敛到业务语义端口后的最小基础设施能力。

这些类目前还不构成必须立刻继续拆分的 DDD 问题，因为：

- 它们没有把 Spring、DAO、Redis/RabbitMQ 细节重新污染回 domain。
- 现有架构测试已经守住了核心边界。
- 继续拆分会开始进入“为了行数拆类”的低收益阶段。

### 二、当前更大的问题在业务完备度，而不是代码风格

项目已经有拼团、秒杀、支付、退款、对账、补偿闭环，但仍然不是完整生产交易平台，主要差在业务完备度：

- 对账中心仍是最小闭环：有差错单、重放、忽略、关闭、备注和操作日志，但没有完整权限、审批流、SLA、运营报表。
- 售后模型仍是交易闭环级，不是完整电商售后系统：缺少部分退款细粒度编排、退款审批、履约后退款、三方退款账单深度核对。
- 秒杀当前是“高并发可演示方案”，不是“大促终局方案”：Redis Stream 能覆盖本机可靠削峰和 pending 补偿，但生产大促更适合 RocketMQ/Kafka/Pulsar。

### 三、最大诚实边界仍然是生产容量和真实多机验证

本机已经具备：

- JDK 1.8 编译运行。
- Docker MySQL/Redis/RabbitMQ 本地环境。
- 秒杀/拼团压测脚本。
- 资源水位采集。
- 本地 OpenTelemetry + Jaeger。

但这仍然不能证明：

- 真实生产 QPS。
- 多实例部署后的抖动和堆积恢复。
- 跨机网络、磁盘 IO、慢 SQL、MQ 大量堆积下的稳定性。

这不是代码没写完，而是环境边界决定当前只能做到趋势验证。

## 优先级排序

### P0：当前最值得持续关注的问题

1. 入口用例支撑类偏厚，但暂不继续拆，先靠架构测试守边界。
2. Redis 通用基础设施接口偏大，后续新增 Redis 能力时禁止继续往公共接口堆方法。
3. 秒杀消息系统仍是 Redis Stream 主方案，面试和文档里必须诚实说明它不是大促终局 MQ。

### P1：业务完备度问题

1. 对账后台缺权限、审批流、SLA 和运营视角。
2. 售后模型不是完整电商售后。
3. 支付渠道现在以 `mock/alipay` 为主，适合本地演示，不等于完整支付中台。

### P2：环境边界问题

1. 本机压测不能代表生产容量。
2. 还没有真实多实例、多节点、真实网络抖动下的稳定性证明。
3. 还没有独立 Linux 压测机和固定资源水位曲线。

## 建议策略

下一阶段不建议再继续进行大规模 DDD 拆分类治理，而应切到“审计 + 守边界”模式：

- 新功能优先检查是否会重新污染 domain 边界。
- 文档和面试材料必须明确哪些是已完成能力，哪些是当前边界。
- 只有当某个类重新开始同时承担多种业务职责、影响测试和维护成本时，再做增量拆分。

## 面试表达

可以直接这样说：

> 这个项目当前最大的价值，不是把每个类拆到最小，而是已经把最危险的边界问题治理掉了：domain 去 Spring、通用大 Repository 删除、状态机和补偿链路独立、架构守护可执行。现在剩下的主要问题不再是代码层面的 DDD 污染，而是业务完备度和生产边界，比如对账中心还是最小闭环、售后不是完整电商售后、秒杀消息系统还停留在 Redis Stream 主方案、本机压测不能证明生产容量。这些问题我会诚实说明，不会硬包装成“已经满分”。
