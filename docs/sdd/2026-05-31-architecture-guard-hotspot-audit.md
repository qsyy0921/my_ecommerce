# 架构守护热点审计

## 背景

继续审核到这个阶段，业务主链路、仓储拆分、Controller 编排、消息端口和补偿台都已经审过多轮。下一层更值得关注的是：

- 守护体系本身是否开始变成新的维护风险。

当前项目的 DDD 守护主要有两层：

- `scripts/check-domain-purity.ps1`
- `DomainPurityTest`

这套守护很有价值，但现在也出现了新的边界问题。

## 审计结论

### 1. `DomainPurityTest` 已经从“架构护栏”演进成“大型字符串规则清单”

当前 [DomainPurityTest.java](/E:/java/qsyy-ecommerce-platform/group-buy-market-master/group-buy-market-app/src/test/java/cn/bugstack/test/architecture/DomainPurityTest.java) 已经超过 2000 行。它覆盖了很多真实有效的守护：

- domain 不依赖 Spring；
- 通用仓储保持删除；
- 语义端口不回流；
- Controller 不重新承担校验、组装和日志；
- MQ、库存、补偿、对账等拆分边界保持稳定。

问题不在“有没有用”，而在它的形态已经开始变重：

- 大量规则基于 `source.contains("...")` 这类字符串匹配。
- 很多断言是“禁止某个类里出现某个片段”，可维护性依赖文件名和文本稳定。
- 规则持续累加后，单文件已经变成巨大回归清单。

这会带来几个真实风险：

- 新人很难快速判断一条失败到底是架构违规，还是字符串守护写得过于脆弱。
- 小规模重命名、日志调整、变量名变化，都可能导致守护需要同步维护。
- 继续往这个类里无限增加规则，会让“架构测试”慢慢变成“项目文本快照测试”。

当前结论：这是守护体系里最明确的新热点。

### 2. `check-domain-purity.ps1` 和 `DomainPurityTest` 有职责落差，不是重复，而是守护层级不一致

当前脚本 [check-domain-purity.ps1](/E:/java/qsyy-ecommerce-platform/scripts/check-domain-purity.ps1) 很轻，只检查：

- Spring 相关依赖
- `@Resource`
- `@Autowired`
- `@Value`
- `ThreadPoolExecutor`

而 `DomainPurityTest` 已经承担了更细的结构守护。

这本身不是问题，但两者的职责差异现在比较大：

- PowerShell 脚本更像“快速粗筛”。
- `DomainPurityTest` 更像“精细边界回归测试”。

真实问题在于，这个分层关系目前只存在于事实里，没有被明确建模：

- 哪些规则应该放在脚本层，哪些应该放在测试层，没有稳定原则。
- 后续继续加守护时，很容易继续把所有事情都堆进 `DomainPurityTest`。

当前结论：不是要合并，而是需要在文档里明确“粗筛”和“精细守护”的边界。

### 3. 当前架构守护非常依赖文本片段，不够语义化

`DomainPurityTest` 当前大量规则像这样：

- 禁止某个文件包含某段 import。
- 禁止某个类里出现某个 builder。
- 禁止某个 Controller 里出现某个 service 调用名。

这类守护在快速治理阶段很有效，因为实现成本低、覆盖面广。但它天然有局限：

- 它判断的是“文本没有出现”，不是“职责真的被隔离”。
- 如果代码换了调用路径、封装层或命名方式，测试可能误报，也可能漏报。
- 当项目继续演进时，维护成本会上升。

所以要诚实说：当前守护是“足够实用”，但不是“最优雅”。

更长期的方向应该是：

- 把最核心的规则逐步抽成更稳定的文件存在性、接口存在性、包依赖和测试契约守护。
- 只把最难结构化表达的边界，继续保留为字符串级禁止规则。

### 4. 守护体系目前仍值得保留，问题在于“继续扩展方式”而不是“现有价值”

这点必须说清楚：虽然 `DomainPurityTest` 已经偏大，但它现在仍然是有价值的。

原因很简单：

- 当前项目的大量拆分，本来就很容易回流。
- 如果没有这些护栏，后续继续改秒杀、拼团、对账、支付时，很容易把旧模式重新塞回去。
- 在“本机长期演进项目”里，这种粗粒度守护比完全没有护栏强很多。

所以当前不是删掉它，而是：

- 继续承认它有用；
- 同时明确它已经进入“守护热点”状态；
- 后续新增规则时要更克制，优先考虑是否能用更稳定的守护方式表达。

## 优先级判断

当前守护体系里的问题优先级是：

1. `DomainPurityTest` 过大且字符串规则过多，是最明确的维护热点。
2. PowerShell 脚本和 JUnit 测试之间的职责边界没有被明确表达。
3. 文本片段守护过多，长期语义稳定性一般。

但这些都属于“守护体系演进问题”，不是主业务代码腐化。

## 本轮结论

继续审核之后，一个新的事实已经明确：

- 现在项目的主要风险不只在业务代码里。
- 守护体系本身也开始出现“大而全”的趋势。

所以后续如果还要继续加架构测试，最应该先问的问题不是“还能不能再加一个 contains 断言”，而是：

1. 这条规则是否真的属于 `DomainPurityTest`？
2. 能不能用更稳定的文件存在性、接口边界或契约测试表达？
3. 会不会让守护体系自己变成新的屎山？

## 面试表述

如果面试官继续深挖“你怎么保证 DDD 不回退”，我不会只说“我加了架构测试”。我会补一句：现在项目里已经有 `check-domain-purity.ps1` 和 `DomainPurityTest` 两层守护，其中 `DomainPurityTest` 很有效，但也已经变成一个 2000 多行的大型规则清单。它能挡住回归，但我也会诚实说明它开始有维护成本，后续要避免继续无节制地往里堆字符串规则。这种表达比单纯说“我有测试护栏”更真实。
