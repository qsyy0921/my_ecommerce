# 生产容量边界保留

日期：2026-05-30

## 背景

当前只有一台 Windows 机器和 Docker Desktop。本机可以做接口可用性、并发趋势、库存不变量、资源水位和补偿链路验证，但不能证明生产容量。生产容量需要独立压测机、多实例服务、独立 Redis/MySQL/MQ 节点、固定资源配额和可归档监控曲线。

## 当前本机能证明什么

- 秒杀链路具备 Redis 预扣、防重、异步排队、pending 回收、失败隔离、批量落库和库存流水审计能力。
- 拼团链路具备试算、锁单、结算、退单、队伍库存占位和补偿能力。
- 本机压测脚本可以观察 QPS 趋势、P95、错误率、库存不变量和资源水位。
- JDK 1.8 编译、domain purity、架构测试和核心领域测试可以作为代码门禁。

## 当前不能证明什么

- 不能证明生产峰值 QPS。
- 不能证明多实例负载均衡后的真实容量。
- 不能证明独立 Redis/MySQL/RabbitMQ 节点的生产瓶颈。
- 不能证明跨机房、网络抖动、磁盘 IO、真实慢 SQL、真实 MQ 堆积下的容量边界。

## 面试表达

可以说：

> 本机压测只能作为趋势验证，不是生产容量承诺。项目当前更有价值的是把高并发链路的正确性、幂等、补偿、可观测和 DDD 边界补齐。真实生产容量我会在独立 Linux 压测机、多服务实例、独立 Redis/MySQL/MQ 和固定资源水位条件下重新压测归档。

不要说：

> 本项目已经证明能抗生产大促。

## 后续生产验证条件

- 至少一台独立压测机，避免压测客户端和服务端抢 CPU。
- 服务多实例部署，固定 JVM 堆、线程池、连接池。
- Redis、MySQL、MQ 独立节点或独立容器配额。
- Prometheus/Grafana 记录 QPS、P95/P99、错误率、CPU、内存、GC、连接池、Redis/MQ/MySQL 水位。
- 压测后保存报告、参数、代码版本、机器规格和不变量校验结果。
