# 锁单幂等等待与装配边界审计

## 背景

继续审核时，单纯看“哪个类大”已经不够了。当前更值得关注的是：

- 核心交易路径里是否还保留阻塞式技术等待。
- app 配置层和 trigger 入口是否已经越过合理边界。

本轮重点看了：

- `TradeLockOrderService`
- `DomainServiceConfig`
- `LoginController`

## 审计结论

### 1. `TradeLockOrderService` 里保留了阻塞轮询等待，这是当前拼团主链路最具体的残留问题

当前拼团锁单幂等路径是：

1. 先尝试获取 Redis 请求锁。
2. 如果没拿到锁，进入 `waitLockResult(...)`。
3. `waitLockResult(...)` 里固定循环 5 次，每次 `Thread.sleep(50L)`。
4. 每次轮询都查缓存结果，查不到就继续等。

这条链路的问题已经不只是“代码风格”，而是明确的技术残留：

- `Thread.sleep(50L)` 直接出现在 domain service。
- 等待策略是固定次数 + 固定间隔，属于同步阻塞式幂等等待。
- 这种实现对单机演示够用，但它会把请求线程挂住最多 250ms。
- 并发上来之后，这种等待模式会放大线程占用和 RT 抖动。

这里要说清楚，它现在为什么还没有坏到必须立刻改：

- 这个等待只发生在“锁没抢到”的幂等竞争场景，不是所有请求都走。
- 它的目标明确，就是给前一个持锁请求一点时间把锁单结果写入缓存或落库。
- 当前本机项目规模下，它比引入更复杂的异步通知或长轮询协议简单得多。

但从架构角度看，这已经是拼团主链路里最具体、最应该诚实记录的残留问题之一。

更好的长期方向应该是：

- 把等待策略抽成独立端口或策略对象，而不是把 `sleep` 写在领域服务里。
- 或者把“结果等待”改成更明确的短轮询适配器/应用层等待逻辑。
- 再进一步，演进成客户端重试或异步结果查询，而不是服务端阻塞等待。

### 2. `TradeLockOrderService` 的幂等链路测试覆盖了正确性，但没有专门覆盖“等待超时”语义

当前 `TradeLockOrderServiceUnitTest` 已经覆盖：

- 重复请求直接命中缓存；
- 活动不可用；
- 用户参与次数上限；
- 队伍满员；
- Redis 占位失败；
- DB 唯一索引冲突回滚；
- 新开团、参团成功。

但它没有单独验证：

- 没拿到请求锁；
- 缓存里也一直没有结果；
- `waitLockResult(...)` 等满 5 次后抛 `E0010`。

这不是 bug 证据，但说明当前测试更偏业务正确性，还没有把“阻塞等待策略本身”当成需要固化的架构语义。

当前结论：后续如果继续治理拼团主链路，应该优先给这条等待路径补独立单测，再决定是否重构等待策略。

### 3. `DomainServiceConfig` 当前仍然是合理的 app 层装配点，不应误判成 DDD 问题

这次顺带看了 `DomainServiceConfig`。

它当前主要做的是：

- 用 Spring Bean 装配领域服务；
- 把端口和规则链注入到 domain service；
- 通过 `@Value` 传入少量配置，比如秒杀单活动最大并发。

这不是当前问题点，原因很明确：

- 它属于 app/config 层，本来就应该负责装配。
- 它没有重新写业务逻辑，没有直接操纵 DAO、缓存、MQ。
- 领域对象继续保持无 Spring 注解，由 app 层统一组装。

所以这里不应该因为“类里 new 了几个 service”就误判成 DDD 腐化。

更准确的判断是：

- `DomainServiceConfig` 目前是健康的装配层。
- 如果后续继续扩展太多 Bean，最多是“装配热点”，不是领域污染。

### 4. `LoginController` 仍保留传统轻量入口风格，但优先级低于交易主链路

`LoginController` 现在还是比较传统的入口风格：

- 每个接口自己 try/catch；
- 自己组装 `Response<String>`；
- 自己判断 `StringUtils.isNotBlank(openidToken)`。

这当然不如已经拆过的交易入口那样规整，但它当前的问题级别要说清楚：

- 它不在秒杀、拼团、支付、对账主交易闭环上。
- 它没有明显越层，不直接操作 DAO、MQ 或缓存。
- 它更像一个“还没做过入口治理的轻量认证接口”，而不是当前系统最危险的腐化点。

所以这里暂时不建议优先动。交易主链路的问题明显更重要。

## 优先级判断

本轮确认后的优先级是：

1. `TradeLockOrderService` 的阻塞轮询等待，是当前拼团主链路最具体的残留问题。
2. `TradeLockOrderService` 缺少等待超时语义测试，是后续可以补的低风险验证项。
3. `DomainServiceConfig` 目前不是问题，只是需要继续保持装配层定位。
4. `LoginController` 仍偏传统，但优先级低。

## 本轮结论

当前继续审核后，一个比之前更具体的事实已经很清楚：

- 拼团主链路剩余的问题，不只是“大类风险”。
- 其中已经有一条可以明确点名的技术残留：`TradeLockOrderService` 的阻塞式幂等等待。

这类问题比“再拆小类”更值得记录，因为它直接关系到：

- 请求线程占用；
- RT 抖动；
- 并发竞争时的表现；
- 未来是否继续把等待策略写进 domain service。

## 面试表述

如果面试官继续追问“现在还有什么具体问题”，我会讲一个更落地的点：拼团锁单幂等路径里，`TradeLockOrderService` 还保留了固定 5 次、每次 50ms 的阻塞轮询等待。这不是功能 bug，但它说明主链路里仍有同步等待策略残留。当前规模下够用，但并发一高就会带来线程占用和 RT 抖动。相比继续机械拆类，这种问题更值得诚实指出，也更接近真实工程审计。
