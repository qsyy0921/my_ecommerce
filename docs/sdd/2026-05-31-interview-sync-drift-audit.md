# 面试文档同步漂移审计

## 背景

继续审核时，除了代码和 SDD 文档本身，我又检查了 [interview-baguwen.md](/E:/java/group_buy_market/docs/interview-baguwen.md) 与最近几轮 `docs/sdd` 审计文档之间的口径是否一致。

当前结论是：

- 八股文档的大方向是对的；
- 但它还没有完全吸收最近几轮更细的剩余问题审计；
- 开始出现“SDD 文档已经更细，面试口径还停留在上一层抽象”的同步漂移。

这不是功能问题，但会直接影响：

- 面试时的真实表达；
- 项目复盘时的口径一致性；
- 后续继续维护时，哪个文档才是最新认知。

## 审计发现

### 1. 八股文档已经写了“还有问题”，但粒度还不够细

当前八股文档已经明确说了：

- 不要说已经满分；
- 秒杀主削峰链路仍以 Redis Stream 为主；
- 本机压测不能代表生产；
- 对账中心和售后还是最小闭环。

这些口径是对的。

但最近几轮 SDD 审计已经把剩余问题进一步细化到了：

- `TradeLockOrderService` 的阻塞轮询等待；
- `DomainPurityTest` 本身已经变成大型字符串规则清单；
- SDD 文档体系存在历史验证快照过多、当前基线分散的问题；
- `GroupBuyActivityDiscountVO` 仍保留字符串协议解析；
- `IRedisService` / `RedissonService` 是超宽基础设施接口风险。

这些点当前在八股文档里还没有被完整同步。

### 2. 八股文档现在更像“架构成就总结”，但最新审计已经开始进入“诚实残留问题清单”

八股文档当前的主旋律是：

- 讲清楚架构做了什么；
- 讲清楚拼团、秒杀、支付、对账、补偿闭环；
- 最后再补一句“还不是满分”。

而最近几轮 SDD 审计，已经进入了更严格的层次：

- 不只说“还有边界”，而是明确点名剩余问题具体在哪。

例如：

- 拼团主链路里的固定阻塞等待；
- 架构守护体系自己开始变大；
- 文档证据漂移。

这说明八股文档和 SDD 审计文档之间已经出现了“抽象层级差”。

### 3. 如果不继续同步，面试文档会慢慢变成“只讲亮点，不讲最新短板”的版本

当前八股文档还没有失真，但已经有这个趋势：

- 亮点部分持续很完整；
- 最新短板没有同步到同样细粒度。

这会导致一个问题：

- 代码和 SDD 审计已经更诚实；
- 但面试文档仍然停在“宏观边界”层面。

后续如果继续积累新审计而不回写八股文档，这份文档就会越来越像宣传材料，而不是当前工程判断。

## 本轮结论

当前项目还需要继续守住一个原则：

- `docs/interview-baguwen.md` 不能只同步亮点，也必须同步最新剩余问题。

否则会出现：

- SDD 文档说得更严谨；
- 面试文档说得更乐观；
- 两套口径同时存在。

这就是典型的文档同步漂移。

## 当前建议

本轮先记录这个问题，不大规模重写八股文档。

后续更合理的动作是：

1. 在八股文档的“当前仍存在的问题”一节继续补充最近几轮更细的残留问题。
2. 保持“亮点”和“短板”同步更新，而不是只更亮点部分。
3. 把八股文档视为“对外口径文件”，要求它始终和 `tasks.md` / `ddd-sdd-todo-list.md` 的现态判断一致。

## 验收

- 本轮只新增审计文档，不修改生产代码。
- `README.md`、`ddd-sdd-todo-list.md`、`tasks.md` 同步记录本轮结论。
- Git 工作区保持可提交状态。

## 面试表述

如果从工程管理角度继续往下讲，我会说：这个项目不仅要防代码回退，还要防口径回退。因为 SDD 审计文档会越来越细，如果八股文档不持续同步最新短板，它就会慢慢只剩亮点总结，跟真实工程状态脱节。对我来说，面试文档也应该是工程事实的一部分，而不是单纯包装材料。
