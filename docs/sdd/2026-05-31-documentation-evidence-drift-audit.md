# 文档证据漂移审计

## 背景

继续审核到现在，代码热点、模型热点、领域编排热点、守护体系热点都已经记过多轮。再往下看，一个新的问题开始出现：

- 文档里的“验证结果”越来越像阶段性历史快照，而不是当前始终成立的事实。

这类问题不会直接让代码出 bug，但会削弱整个 SDD 文档体系的可信度。因为当文档一边强调“按证据说话”，另一边又保留大量过期的测试数量和阶段性通过结论时，后续读者很难区分：

- 哪些是当前仍成立的结论；
- 哪些只是当时那一轮提交前的结果。

## 审计发现

### 1. 多份 SDD 文档记录了不同时间点的测试数量，这些数字现在是历史快照，不应继续被当成当前真相

当前可以直接看到很多文档里写了：

- `DomainPurityTest` 28 个测试通过
- 29 个测试通过
- 30 个测试通过
- 31 个测试通过
- 36 个测试通过
- 41 个测试通过

这些都不一定是错的，它们在各自那一轮提交时很可能是真的。但现在它们的问题是：

- 同一测试集随着规则增加，数量已经变化很多次；
- 老文档里的数字不再能代表当前状态；
- 如果读者不区分“历史验证结果”和“当前基线”，就会误读。

所以这些数字当前更准确的含义是：

- “当时这一轮改动的验证快照”

而不是：

- “当前仓库最新测试基线”

### 2. 许多文档写了“编译通过”“测试通过”，但没有明确说明这是阶段性证明还是当前持续保证

例如很多文档会写：

- JDK 1.8 编译通过
- domain purity 脚本通过
- 架构测试通过
- 对账契约测试通过

这类表述在单篇变更记录里没问题，但随着文档越来越多，开始出现两个隐患：

- 同样的表述在几十篇文档里反复出现，很容易被读成“当前全部仍已统一验证”。
- 一旦后续有人只看文档，不重新跑测试，就可能拿历史通过当成现态证据。

这不是文档写错了，而是文档类型没有被明确区分：

- 有些文档是“变更记录”。
- 有些文档是“当前状态说明”。

现在这两类内容混在一起了。

### 3. `README.md`、`tasks.md`、`ddd-sdd-todo-list.md` 更接近当前状态，但大量按日期命名的审计文档本质上是历史增量记录

目前文档体系里至少有三层内容：

1. `README.md`：入口索引
2. `tasks.md` / `ddd-sdd-todo-list.md`：更接近当前状态
3. `2026-05-30-*.md`、`2026-05-31-*.md`：具体某一轮改动或审计记录

真正的问题不在于有历史记录，而在于：

- 这三层之间“当前状态”和“历史快照”的边界没有被明确说清楚。

所以继续演进下去，最容易出现的情况是：

- 最新结论在 `tasks.md`
- 老的阶段性数字在某篇审计文档
- 面试材料或读者混用两者，造成证据漂移

### 4. 现在最缺的不是更多审计，而是一个“当前权威验证基线”的收敛点

继续加单篇审计文档没有问题，但如果没有一个稳定的“当前权威验证基线”，后续文档会越来越像变更日志集合。

从当前结构看，更适合作为“当前权威基线”的只能是：

- `tasks.md`
- `ddd-sdd-todo-list.md`
- 或单独新增一个 `current-verification-baseline.md`

而不是继续让每篇审计文档都各自写一套“当时通过了哪些测试”。

## 审计结论

当前文档体系的核心风险不是缺内容，而是：

- 历史验证快照过多；
- 当前权威基线不够集中；
- 读者容易把“当时通过”误读成“现在仍证明”。

这已经是一个真实的工程文档问题，尤其是在项目不断迭代、审计文档持续增加的情况下。

## 当前建议

本轮先只记录问题，不大规模改旧文档。

原因：

- 旧文档本来就是按日期记录的变更审计，保留历史快照有价值。
- 直接回头把所有旧文档里的数字都改掉，会破坏历史上下文，也收益不高。

更合理的方向是：

1. 在入口文档或任务文档里明确区分“当前状态”和“历史记录”。
2. 后续新增审计文档时，减少重复写“当前全部通过”这类泛化表述。
3. 如果后面继续治理文档体系，再新增一个专门的“当前验证基线”文档，把真正权威的现态结果集中收敛。

## 优先级判断

这个问题的优先级低于主业务代码和高并发链路，但高于继续机械补更多历史审计。

原因很简单：

- 如果文档证据开始漂移，后续审计本身的可信度会下降。
- 项目越大、文档越多，这个问题会越明显。

## 本轮结论

继续审核之后，当前项目除了代码热点、测试热点之外，又多了一个应当诚实记录的事实：

- SDD 文档体系已经开始出现“历史快照过多、当前证据基线分散”的问题。

这不影响系统运行，但会影响项目说明、面试表达和后续维护判断的准确性。

## 验收

- 本轮只新增审计文档，不修改生产代码。
- `README.md`、`ddd-sdd-todo-list.md`、`tasks.md` 同步记录本轮结论。
- Git 工作区保持可提交状态。

## 面试表述

如果要从工程管理角度再往下讲，我会补一句：这个项目现在不仅要防代码回退，也要防文档证据漂移。因为我已经积累了很多按日期的 SDD 审计文档，里面有不少“当时测试通过”的阶段性结论。后续必须把“历史快照”和“当前权威基线”分开，否则文档会越来越多，但证据反而越来越分散。这种问题不影响功能，却会直接影响项目的可维护性和可解释性。
