# 审计优先级拉平风险审计

## 背景

继续审核到现在，`docs/sdd` 下已经不只是“文档越来越多”，还出现了另一个更隐蔽的问题：

- 问题很多都被记录了；
- 但这些问题之间的主次关系开始变得不够清晰。

当前 `2026-05-31-*.md` 审计文档已经达到 32 篇，其中多篇文档都单独写了“优先级判断”或“当前结论”。这说明局部判断是存在的，但整体优先级视图并没有真正收敛成一张图。

## 审计发现

### 1. 局部文档在排序，但全局问题没有统一排序

现在的文档体系里，已经能看到很多局部优先级表达：

- `current-ddd-business-gap-audit` 给出了 P0/P1/P2；
- `gateway-and-domain-orchestration-audit` 有自己的优先级判断；
- `lock-idempotency-and-assembly-boundary-audit` 有自己的优先级判断；
- `architecture-guard-hotspot-audit`、`documentation-evidence-drift-audit`、`audit-fragmentation-risk` 也都有优先级表达。

问题在于：

- 这些排序大多只在各自文档内部成立；
- 但跨文档时，并没有一个统一的“当前前 5 个问题”。

结果就是：

- 每篇都在排优先级；
- 但全局上反而更容易被看成“都很重要”。

### 2. 已完成审计任务越来越多，但“现在最该盯什么”反而不够直观

`tasks.md` 和 `ddd-sdd-todo-list.md` 现在记录了大量“已完成审计结论”。

这本来是好事，说明问题不是没看到，而是已经被系统化记录。

但副作用也开始出现：

- 审计项大多已经打成 `[x]`；
- 读者更容易把它理解成“都处理过了”；
- 却不一定能快速看出“哪些只是被识别和记录，哪些才是真正应该持续盯住的残留风险”。

也就是说，当前文档体系更擅长表达：

- 我们发现了什么；

但还不够擅长表达：

- 现在最值得优先关注什么。

### 3. 低优先级问题被写得足够多时，容易和高优先级问题在感知上拉平

目前已经出现这种倾向：

- `TradeLockOrderService` 阻塞轮询等待这种交易主链路问题；
- `IRedisService` / `RedissonService` 这种基础设施大接口问题；
- 文档证据漂移、审计碎片化、面试同步漂移这类治理问题；

它们都已经被写成正式审计文档。

这有价值，但也带来一个风险：

- 如果没有统一优先级地图，读者可能会把它们理解成同一层级的问题。

实际上并不是。

例如当前更合理的判断应该是：

1. 交易主链路和基础设施边界问题优先级更高；
2. 业务完备度问题其次；
3. 守护体系和文档体系问题再其次；
4. 纯口径同步问题优先级最低。

如果不把这层关系重新讲清楚，文档越完整，优先级越容易被拉平。

### 4. 当前缺的不是继续补“问题列表”，而是补“剩余问题排序视图”

前面几轮审核已经把问题列表补得很完整了：

- 代码热点；
- 守护热点；
- 文档漂移；
- 面试同步；
- 碎片化风险；
- 主链路等待策略；
- 基础设施大接口；
- 业务完备度边界；
- 环境边界。

所以现在真正缺的已经不是“再列更多问题”，而是把这些问题做一次更明确的排序收敛：

- 哪些是必须长期盯住的架构风险；
- 哪些是需要诚实说明但不急着动的业务边界；
- 哪些是工程治理层面的次级问题。

## 审计结论

当前项目已经开始出现“优先级拉平风险”：

- 问题不是没记录；
- 而是记录得越完整，主次越容易被写平。

这不是代码问题，也不是文档正确性问题，而是“剩余问题管理视角”问题。

## 当前建议

本轮仍然只记录问题，不重构文档体系。

但如果后续继续审核，更合理的增量动作应该是：

1. 在 `tasks.md` 或单独文档里形成“当前前 5 个残留风险”。
2. 把剩余问题至少分成四层：交易主链路、基础设施边界、业务完备度、文档/口径治理。
3. 后续新增审计文档时，避免默认给每个问题都同样的篇幅和正式程度。

## 优先级判断

这个问题本身的优先级：

- 低于交易主链路真实风险；
- 低于基础设施大接口继续膨胀风险；
- 高于继续无限追加新的局部审计。

因为如果优先级继续被拉平，后续审计虽然越来越多，但指导价值会下降。

## 本轮结论

继续审核之后，现在可以再补一个更细的判断：

- 当前 SDD 体系的问题已经不只是碎片化；
- 还包括“剩余问题主次不够收敛”。

下一步更值得做的，不一定是继续新增单点问题，而可能是开始把这些问题重新排出清晰顺序。

## 验收

- 本轮只新增审计文档，不修改生产代码。
- `README.md`、`ddd-sdd-todo-list.md`、`tasks.md` 同步记录本轮结论。
- Git 工作区保持可提交状态。
